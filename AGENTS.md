## Как вносим изменения

### Ветки и PR

- Любое изменение - в своей ветке, имя по сути, без префиксов (`keep-in-touch`); в main только через PR
- «Начинаем фичу / доработку / правку» и `/opsx:propose` - переключись на main, забери изменения, удали локальные ветки, которых уже нет на GitHub; новая ветка от свежего main
- Перед первой правкой файлов проверь ветку: на main - забери изменения и создай новую ветку от свежего main; в рабочей ветке - продолжай в ней; ветка уже влита - новая от свежего main
- «Коммить и пуш» - коммит в текущую ветку, push, PR в main; дай ссылку на PR
- PR открыл - сразу включи автовлитие (`gh pr merge --auto --squash`): вольётся сам после зелёного CI. Не включай, если владелец сказал вливать позже. Автовлитие недоступно - скажи владельцу
- После merge - переключись на main, забери изменения, удали ветку локально
- Изменения выкатки (workflows, скрипты в `deploy/`) - тем же путём, через PR

### Правка и фича

- Мелкая правка, в том числе небольшое изменение модели данных - план в режиме планирования, ветка, PR, CI
- Фича - полный цикл: требования → план → реализация по шагам. Инструмент любой, например OpenSpec
- Фича готова, когда выполнены критерии приёмки из её спеки

### Тесты и CI

- TDD для кода приложения: сначала тест, он красный → код → тест зелёный
- Сервер, скрипты выкатки и CI - без автотестов: проверяем настоящей выкаткой
- e2e без моков, на настоящей базе в Docker
- Тест создаёт все данные, на которые опирается, и удаляет их сам; на сид и содержимое локальной базы не полагается: в CI база пустая
- CI на каждый PR: lint, формат, типы, Vitest, Playwright, сборка образа
- Красный CI в main не вливается
- Красный CI - чинить причину. Не отключать, не удалять и не ослаблять тесты и проверки

### Проверки

- `pnpm typecheck`, `pnpm test` - после каждого шага
- Полный прогон перед PR - `zsh scripts/checks.sh`: повторяет CI на свежей пустой базе (lint, формат, типы, Vitest, сборка, e2e; кроме сборки образа), вывод в `tmp/checks.log`; скриншоты эскизов - `zsh scripts/mockup-shots.sh`, вывод в `tmp/shots/`. Оба скрипта только локально, не в git
- Перед сборкой остановить `pnpm dev`: сборка и dev пишут в одну `.next`. Если `pnpm dev` пишет «Port 3000 is in use» - на 3000 висит старый сервер (стили там отдают 500), остановить его

### Проверка в браузере

- Живое приложение (ховер, фокус, формы) - через Claude in Chrome на `localhost:3000`; расширение подключает владелец
- Данные в базе не создавать: ошибки проверять пустыми формами; сохранение покрывают e2e
- Команды расширению - по одной, не пачкой; открыта только своя вкладка с расширением. Иначе действия падают с «Couldn't determine which page this action targets»
- Окно не шире 937px, `resize_window` его не сужает: ширину 390 смотреть через iframe 390px, вставленный в страницу через `javascript_tool` (как в `scripts/mockup-shots.sh`)
- Фокус с клавиатуры - `el.focus({focusVisible: true})`; стиль читать через ~400ms: `transition-colors` анимирует и цвет рамки

### Окружения и сервер

- Окружения: локальное, тест-стенд (https://test-app.mypeoplecrm.ru), прод (https://app.mypeoplecrm.ru) - у каждого своя база, свой `.env` и ключи
- На сервере docker compose, проекты `staging` и `prod` (`-p staging`, `-p prod`); у каждого контейнера лимит памяти
- База тест-стенда - копия базы прода из последнего бэкапа; испортилась - пересоздаём из свежего бэкапа (`deploy/staging-db.sh`); сессии и ссылки входа прода в копию не попадают; письма настоящие, со своим ключом почты; остальные внешние интеграции отключены
- Тест-стенд закрыт паролем в nginx (кроме `/health`), пароль задаёт владелец; сертификат стенда выпускает агент
- Ссылка во входном письме ведёт на адрес того окружения, где запросили вход; кука входа - только на своём поддомене, без общего домена
- Сервер общий для приложения и лендинга: чужие ключи, папки и настройки nginx на нём не удаляй и не меняй - только добавляй своё; удалить - только с согласия владельца
- Логи контейнеров - в журнал сервера (journald): переживают выкатку и откат; размер журнала ограничивает система, старые строки удаляются - диск сервера не забивается
- Логи читаешь сам по ssh, когда прошу; в README - как читать логи

### Как выкатываем

- Скрипты выкатки - в `deploy/` в репо; выкатка копирует на сервер всю папку `deploy/`, новый скрипт уезжает сам; отдельный workflow под скрипты не заводить; в workflow только их вызов
- Один скрипт выкатки и один compose.yml на тест-стенд и прод, окружение - параметром; бэкап только на проде
- Два деплоя на одно окружение параллельно не идут: следующий ждёт текущий
- Merge в main → образ с тегом SHA коммита → GHCR → тест-стенд: миграции → новый образ → smoke `/health`
- На тест-стенд и прод едет один и тот же образ; на прод - только SHA, прошедший тест-стенд: Deploy prod проверяет это по истории выкаток тест-стенда в GitHub
- Deploy prod: поле SHA пустое - катит SHA последней зелёной выкатки на тест-стенд; SHA вручную - запасной путь; галочка «откат» - версию прода до текущей, её помнит сервер, без проверки тест-стенда, поле SHA при этом не смотрим; какой SHA выкатился - в итогах запуска
- Прод: бэкап базы → миграции → образ → smoke
- Миграции - отдельный шаг до старта нового образа: разовый контейнер из того же образа применяет миграции и завершается; упали миграции - новый образ не стартует
- Чистка образов после удачной выкатки на прод: на сервере удаляем образы старше 2 недель, кроме двух последних версий прода и текущей версии тест-стенда; в GHCR храним 10 последних сборок
- После выкатки скажи, как проверить и как откатить

### Сбой и откат

- Красный smoke - выкатка упала, сообщи владельцу. Сам ничего не откатывай, автооткат в скрипты не ставь: откат только вручную, запускает владелец
- Откат на прошлую версию прода работает всегда: образы прошлых версий хранятся на сервере

## Бэкапы

- Бэкап базы раз в сутки в 03:00 по Москве
- Бэкапы перед выкаткой и ежедневные: храним по 7 последних
- Восстановление - только скриптом restore, в пустую базу: удалить базу, создать заново, загрузить бэкап
- Restore - команда на сервере, запускает владелец; на вход файл бэкапа; перед удалением базы показывает, какой файл и какую базу заменит, и ждёт ввода «yes»; снимает копию текущей; останавливает приложение прода, восстанавливает базу, поднимает приложение той же версии; версию приложения не меняет - откат версии через Deploy prod
- Восстановление владелец проверяет сам, регулярно, по инструкции в README
