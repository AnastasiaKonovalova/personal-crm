# Design

## Context

Лимит на адрес (3 письма за 10 минут) живёт в хуке `beforeSignInRequest` (`src/server/auth.ts`). Через этот хук идут и форма (server action вызывает `getAuth().api.signInMagicLink` с `await headers()`), и прямой POST на `/api/auth/sign-in/magic-link`. `takeEmailPlace` считает строки `login_emails` по адресу и вставляет новую в одной транзакции под `pg_advisory_xact_lock(hashtext(email))`. Если отправка не удалась, `giveEmailPlaceBack` удаляет последнюю строку адреса. Строки старше суток удаляются после каждой отправки.

nginx прода и тест-стенда (проверено на сервере 2026-11-25) ставит `X-Real-IP $remote_addr` и `X-Forwarded-For $proxy_add_x_forwarded_for`. Порт приложения открыт только на localhost (`daemon.json`, `"ip": "127.0.0.1"`).

## Goals / Non-Goals

**Goals:**
- Лимит по IP в том же месте и в той же транзакции, что и лимит на адрес: одна точка для формы и прямого запроса, никакой гонки
- IP, который клиент не может подделать

**Non-Goals:**
- Лимит Better Auth по IP на HTTP-входе не трогаем, тест `tests/auth-ip-limit.test.ts` остаётся
- nginx (`limit_req`) не меняем: настройки вне git, сервер общий
- Отдельный текст для лимита по IP не делаем: решение владельца - тот же текст

## Decisions

1. **IP только из `X-Real-IP`.** nginx перезаписывает этот заголовок значением `$remote_addr`, поэтому подставить его клиент не может. В `X-Forwarded-For` nginx дописывает адрес к присланному, и первое значение в нём от клиента. Better Auth по умолчанию берёт как раз первое значение `X-Forwarded-For`, поэтому его `getIp` не используем. Значение обрезается по краям. Пустое значение или отсутствие заголовка = IP неизвестен.
2. **Без IP лимит по IP не действует.** Так бывает только без nginx: локально и в e2e, где тест не ставит заголовок. На сервере в обход nginx до приложения не достучаться. Другой вариант - общий счётчик для неизвестного IP. Он сломал бы e2e: все запросы прогона идут без заголовка, и уже на 11-м письме тесты получили бы отказ.
3. **Колонка `ip text` (может быть пустой) в `login_emails` и индекс `(ip, sent_at)`.** Одна строка - одно письмо, оба лимита считают по одним и тем же строкам. `giveEmailPlaceBack` и чистка через сутки остаются без изменений: место возвращается сразу в обоих лимитах. Отдельная таблица под IP дала бы два места записи и два возврата.
4. **Блокировки: сначала адрес, потом IP, всегда в этом порядке.** Ключи двухаргументные, `pg_advisory_xact_lock(1, hashtext(email))` и `pg_advisory_xact_lock(2, hashtext(ip))`, чтобы хэш адреса не совпал с хэшем IP. Поскольку порядок один, взаимной блокировки нет: транзакция, которая держит блокировку IP, уже держит и блокировку своего адреса и больше ничего не ждёт. Сначала проверяется IP (10 за 60 минут), потом адрес (3 за 10 минут), затем строка вставляется вместе с `ip`. Если упёрлись в любой из лимитов, строка не вставляется. Без IP шаг блокировки по IP пропускается.
5. **Ответ при отказе тот же:** `TOO_MANY_REQUESTS` с кодом `TOO_MANY_LOGIN_EMAILS`. Форма уже превращает его в «Слишком часто, попробуй через несколько минут», `actions.ts` не меняется.
6. **Тесты - e2e в `tests/e2e/login.e2e.ts`, на настоящем приложении и Mailpit.** `requestLoginLink` получает необязательный `ip` и ставит заголовок `X-Real-IP`. В каждом тесте свой выдуманный IP из `198.51.100.0/24` (диапазон для документации), со случайным последним октетом и проверкой, что строк с этим IP ещё нет. Строки и письма удаляет `removeUser`. Сдвиг времени делается только на строках своего IP. Помимо сценариев спеки: 15 одновременных запросов с одного IP - уходит ровно 10 писем; разные `X-Forwarded-For` при одном `X-Real-IP` - один счётчик.

## Risks / Trade-offs

- [За одним IP несколько человек: офис, мобильный оператор] → 10 в час с запасом для личного приложения; число в одной константе
- [Кто-то откроет порт приложения наружу в обход nginx, и `X-Real-IP` можно будет подставить] → сейчас это закрывает `daemon.json`; страховочное правило `DOCKER-USER` уже в бэклоге
- [IPv6: один человек может менять адреса внутри своей /64] → пока считаем по полному адресу; лимит на адрес почты при этом работает

## Migration Plan

- Миграция `0005`: `ALTER TABLE login_emails ADD COLUMN ip text` и `CREATE INDEX`. Существующие строки получают `ip = null` и в лимите по IP не считаются; за сутки они уходят чисткой. Тест на данных в `tests/migration-on-data.test.ts` показывает, что старые строки целы
- Выкатка обычная: тест-стенд → Deploy prod. Откат через Deploy prod с галочкой «откат»: старый код колонку `ip` не читает и не пишет, она может быть пустой
