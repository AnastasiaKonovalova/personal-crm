# Design

## Context

Мотивация - `proposal.md`, требования - `specs/contact-birthdays/spec.md` и дельта `specs/data-ownership/spec.md`.

Что есть сейчас:
- `contacts` в `src/db/schema.ts`: пять текстовых полей, частота (`cadence`, `contact_on` с CHECK), владелец `user_id`. Миграции `0000`–`0003`; каждая новая миграция обязана иметь свой тест в `tests/migration-on-data.test.ts` (`CHECKED_MIGRATIONS`)
- Валидация - zod в `src/lib/validation.ts` (`contactSchemaFor`); ошибки по полям собирает `firstErrors`, форма получает их и введённые значения через `ContactFormState`
- Форма `src/components/contact-form.tsx`: пять текстовых полей, `CadenceFields` (нативный `select` + поле даты, которое с JS видно только при «Конкретная дата», без JS - всегда), `GroupFields`; блоки пересоздаются по `key`, чтобы после ошибки вернуть введённое (React читает `defaultValue` у `select` один раз)
- Блок «Пора связаться»: `listReminders` в `src/server/contacts.ts` берёт контакты с частотой, статусы считает в коде чистыми функциями из `src/lib/keep-in-touch.ts`; страница решает, показывать ли блок (`!query && page === 1 && total > 0`) - одинаково на главной и на странице группы. Клиентский `RemindersBlock` получает все строки, видимые выбирает `blockView` (`src/lib/reminders-view.ts`); строки вне вида скрывает CSS по `data-row-out` только при JS, кнопки с `data-js-only` без JS скрыты
- Даты - строки `YYYY-MM-DD`; `toDateString` (сегодня в `APP_TIME_ZONE`, Москва), `daysBetween`, `pluralDays`, `formatDueDate` - в `src/lib/keep-in-touch.ts`

## Goals / Non-Goals

**Goals:**
- Дата рождения без года - полноценный случай, а не обходной путь
- Расчёт дня рождения и возраста - чистые функции с юнит-тестами, «сегодня» передаётся параметром
- Блок ведёт себя как «Пора связаться» на том же коде раскрытия и пагинации, а не на копии

**Non-Goals:**
- Уведомления и письма о днях рождения (в продуктовой идее «Не делать: уведомления»)
- Отметка дня рождения в строке общего списка
- «Через N дней» и возраст в карточке: там только дата
- Подтверждение перед «Поздравил(а)» и «Связались», сохранение конкретной даты связи при поздравлении - отдельная доработка после выкатки (`specs/backlog.md`)
- Импорт дат рождения из телефона или календаря

## Decisions

### 1. Четыре столбца: `birth_day`, `birth_month`, `birth_year`, `birth_leap_day`

- `birth_day smallint`, `birth_month smallint`, `birth_year smallint` - все необязательные
- `birth_leap_day` - новый enum `birth_leap_day` (`feb_28`, `mar_1`), необязательный: в какой день отмечать 29 февраля в невисокосный год
- CHECK: день и месяц заданы вместе или вместе пусты; год только при заданных дне и месяце; день 1–31, месяц 1–12, год ≥ 1900; `birth_leap_day` задан тогда и только тогда, когда дата - 29 февраля (через `coalesce`, как у `cadence`: сравнение с NULL CHECK пропускает)
- Пятый столбец, `birth_congratulated_on`, - для «Поздравил(а)», п.9
- Существование даты (31 апреля, 29 февраля в невисокосный год) и «не в будущем» проверяет zod: в CHECK такую проверку не выразить без функции, которая падает с ошибкой вместо `false`, а «сегодня» в CHECK меняется со временем

Альтернатива - один столбец `birthday date` и флаг «год неизвестен» с подставным годом (2000, високосный): дата без года становится выдуманной датой, любой запрос и экспорт должен помнить про флаг. Отклонено. Альтернатива для выбора - `boolean` «1 марта»: читается хуже, чем два названных значения. Отклонено.

### 2. Поле в форме - два `select`, поле года и выбор для 29 февраля

Под полями контакта (после «Почта», до «Как часто связываться»; порядок - на эскизе) - «День рождения»: `select` «День» (1–31), `select` «Месяц» (январь–декабрь), поле «Год» (`inputmode="numeric"`, необязательно). Пустые варианты «—» у дня и месяца - «не задано». Одна ошибка на поле целиком, под строкой, как у частоты (решение 19 в `design/README.md`).

Под ними - две радиокнопки «В невисокосный год: 28 февраля / 1 марта», по умолчанию 28 февраля. С JS видны только при 29 февраля - тем же приёмом, что поле даты у частоты (`data-visible` и правило в `globals.css`); без JS видны всегда, сервер учитывает их только при 29 февраля.

- Работает без JavaScript: обычные поля формы, сервер получает `birthDay`, `birthMonth`, `birthYear`, `birthLeapDay` строками
- Блок пересоздаётся по `key` от значений по умолчанию, как `CadenceFields`: после ошибки формы выбор не сбрасывается
- `ContactField` выводится из схемы, поэтому новые ключи сами попадут в типы формы и `ContactFormValues`; страница редактирования переводит числа из базы в строки

Альтернатива - `<input type="date">`, как у частоты: требует год, без года дату не ввести. Альтернатива - одно текстовое поле «дд.мм.гггг»: ошибки ввода чаще, на телефоне неудобно. Отклонены (владелец 2026-11-22); окончательный вид - на эскизе.

### 3. Валидация в схеме контакта

В `contactSchemaFor` - четыре поля: пустая строка → `null`, иначе целое число (выбор - одно из `feb_28`, `mar_1`). `superRefine` по спеке «Проверка даты рождения»: пара день-месяц, существование даты (с годом - в этом году; без года - в високосном, чтобы 29 февраля проходило), год ≥ 1900 и полная дата не позже сегодняшнего дня (`today` - параметр схемы, как у частоты). `transform` оставляет выбор только при 29 февраля, по умолчанию `feb_28` - как `dropStrayDate` у частоты. Ошибка - с путём `birthDay`, форма показывает её под полем целиком. Тексты ошибок - из спеки, в стиле ошибок частоты («Укажи дату»).

### 4. Расчёт - `src/lib/birthdays.ts` поверх функций «Пора связаться»

Берём из `src/lib/keep-in-touch.ts` как есть: `toDateString`, `daysBetween`, `pluralDays`, формат даты без года (тот же `Intl`, что у `formatDueDate`). Окно в 7 дней - общая экспортируемая константа: окно «скоро» у «Пора связаться» и окно блока дней рождения одно число, не расходятся.

Новое, поверх них:
- `birthdayIn(year, month, day, leapDay)` → дата `YYYY-MM-DD`, когда день рождения отмечается в этом году; 29 февраля в невисокосный год → 28 февраля или 1 марта по выбору
- `daysToBirthday(month, day, leapDay, today)` → от −1 до 365: в этом году, если он был вчера или ещё впереди; иначе в следующем. Вчера через Новый год - день рождения прошлого года (31 декабря при 1 января)
- `ageOn(birthYear, celebratedOn)` - год отмечаемой даты минус год рождения
- `sortForBirthdays` - окно от −1 до 7, по дням (вчерашние сверху), затем по имени (`localeCompare(…, "ru")`)
- тексты строки: «Вчера», «Сегодня», «Завтра», «Послезавтра», «Через N дней» (`pluralDays`); «исполнилось / исполняется / исполнится N»

Не берём: `status` и `sortForReminders` - у дня рождения нет «просрочено», общая сортировка связала бы правки двух фич.

### 5. Сервер - `listBirthdays(userId, { groupId })`

Как `listReminders`: контакты пользователя с заданным `birth_month` (и группой, если она есть), расчёт и сортировка в коде; поздравленные к этому дню рождения пропускаются (п.9). Дат рождения у владельца сотни, не тысячи - фильтровать окно в SQL (с переходом через год и 29 февраля) сложнее, а выигрыша нет. `createContact` и `updateContact` сохраняют четыре поля вместе с остальными, отдельного действия нет.

`getContactWithNotes` уже отдаёт весь контакт - строке карточки нужен только формат: «25 ноября 1990», «25 ноября», «29 февраля 1992 · в невисокосный год — 1 марта».

### 6. Блок - `BirthdaysBlock` на общем механизме с «Пора связаться»

- Строки готовит страница (как `reminderRows`): id, имя, текст «когда», дата, возраст
- Клиентский компонент, как `RemindersBlock`: все строки приходят в странице, видимые выбирает `blockView`, строки вне вида скрывает `data-row-out`, кнопки - `data-js-only`. Без JS - все строки, без кнопок
- Нижняя панель (пагинация «Страница X из Y» со стрелками и кнопка «Показать все (N)» / «Свернуть») выносится из `RemindersBlock` в общий компонент; оба блока держат своё состояние раскрытия, листание одного не трогает другой. Перенос страхуют существующие тесты «Пора связаться» (`tests/reminders-block.test.ts`, `tests/browser/keep-in-touch.spec.ts`) - они должны остаться зелёными без правок
- После «Поздравил(а)» строка уходит из блока на месте (п.9), поэтому `BirthdaysBlock` согласует состояние раскрытия с числом строк так же, как `RemindersBlock` после «Связались»: 5 строк и меньше - раскрытие снимается, опустевшая страница - на последнюю
- Вид - как у «Пора связаться» (карточка-список, число у заголовка, строка - ссылка на карточку на всю ширину, ховер `teal-soft`), с кнопкой «Поздравил(а)» поверх строки (п.9); иконка и цвет - на эскизе
- Место - над «Пора связаться»; поиск и фильтр поднимаются над обоими блоками (решение 42 в `design/README.md`). Точки: «Вчера» - как «просрочено», «Сегодня» - как «скоро» (решение 39). Условие показа - то же выражение на главной и на странице группы: первая страница, без поиска, есть контакты; плюс в окне есть хотя бы один день рождения. Пустого состояния нет

### 7. Сид

У части демо-контактов (~30%) - даты рождения, у трети из них без года. Отдельно - даты от дня запуска сида: вчера, сегодня, завтра, послезавтра, через 7 и через 8 дней (граница окна), позавчера; всего в окне больше 10, чтобы была пагинация блока. 29 февраля - у двух контактов, с выбором «28 февраля» и «1 марта». Ещё один контакт с днём рождения в окне уже поздравлен (п.9): в блоке его нет, в карточке - заметка «Поздравил(а)». Имена - выдуманные, как остальной сид.

### 8. Тесты

- Юнит (Vitest): `tests/birthdays.test.ts` - сценарии «Ближайший день рождения» и «Строка блока»; `tests/validation.test.ts` - сценарии «Проверка даты рождения» и «29 февраля в невисокосный год»; разметка блока строкой HTML, как `tests/reminders-block.test.ts`
- Интеграционные на базе: сохранение, очистка и выбор для 29 февраля, `listBirthdays` - порядок, граница окна, группа, чужие контакты
- Миграция: тест `0004` в `tests/migration-on-data.test.ts` - старые контакты без даты, данные те же
- e2e по HTTP (`tests/e2e/`): форма без JavaScript, ошибка с сохранением введённого, карточка, блок на главной и над «Пора связаться», в поиске его нет. «Сегодня» в тестах считается так же, как в приложении; даты строятся от него
- Playwright (`tests/browser/`): раскрытие, пагинация, повторное раскрытие, блок без JavaScript, выбор 29 февраля появляется при выборе даты
- «Поздравил(а)» (п.9): правило скрытия - юнит; `congratulate` и фильтр `listBirthdays` - на базе, включая чужой контакт; действие без JavaScript - e2e по HTTP; строка уходит на месте - Playwright. Тесты keep-in-touch остаются зелёными без правок
- Карта сценариев и тестов - `coverage.md` в конце

### 9. «Поздравил(а)»

Решения владельца (2026-11-24): кнопка только в строке блока; нажатие - заметка «Поздравил(а)» тем же путём, что «Связались», и всё, что keep-in-touch делает после заметки, не меняется (срок пересчитывается, наступившая конкретная дата снимается); строка уходит из блока до следующего дня рождения; без JavaScript форма отправляется сразу; подтверждения пока нет.

- Пятый столбец `birth_congratulated_on date` в `contacts`, необязательный, без CHECK: день последнего поздравления по `APP_TIME_ZONE`. Строка скрыта, если он не раньше, чем за `SOON_DAYS` до отмечаемой даты (`nextBirthday(...).on`): поздравить можно только из блока, то есть не раньше чем за 7 дней, а к следующему году правило перестаёт срабатывать само. Чистая функция в `src/lib/birthdays.ts`, «сегодня» - параметр
- Сервер: `congratulate(userId, contactId)` в `src/server/contacts.ts` - одна транзакция: дата поздравления и заметка «Поздравил(а)». Заметка пишется той же функцией, что у `addNote` (вынести её тело в функцию от транзакции), поэтому снятие конкретной даты и расчёт срока остаются общими, а не копией. Чужой или несуществующий контакт - ничего не меняется
- Действие `congratulateAction` в `src/app/contacts/actions.ts`, как `markContactedAction`: с JavaScript страница обновляется на месте; без него - редирект обратно на ту же страницу (главная, `/?group=…` или страница группы). Адрес возврата проверяет сервер: только `/`, `/?group=<uuid>`, `/groups/<uuid>`, иначе - `/`
- Кнопка - как `MarkContactedButton`: ghost, иконка Lucide `cake` и «Поздравил(а)», на ≤560 только круглая иконка 44px, `aria-label` «Поздравил(а): <имя>»; поверх ссылки строки (`z-1`), как «Связались»

Альтернативы: искать заметку «Поздравил(а)» по тексту - ломается от правки заметки или такого же текста, набранного руками (владелец выбрал столбец); отдельная таблица поздравлений - история не нужна, только последнее. Отклонены.

## Risks / Trade-offs

- [Тест упадёт около полуночи по Москве: «сегодня» в тесте и в запросе разное] → тест считает даты от `toDateString(new Date())` в момент запроса и проверяет строку блока по контакту, а не по числу дней; для чистых функций «сегодня» - параметр
- [Возраст неверен, если год ввели с опечаткой] → год ≥ 1900 и не в будущем; остальное - на совести владельца, видно в карточке
- [Вынос нижней панели из `RemindersBlock` сломает «Пора связаться»] → существующие тесты блока не правятся и должны остаться зелёными; вынос - отдельным шагом до нового блока
- [Два блока подряд отодвигают поиск и список вниз] → оба свёрнуты до 5 строк; вид на 1280 и 390 - на эскизе до кода
- [Два `select`, поле года и радиокнопки на узком экране] → вид на 390 - на эскизе до кода

## Migration Plan

- Миграция `0004` добавляет enum и пять столбцов (четыре даты рождения и `birth_congratulated_on`) без `NOT NULL` и без значения по умолчанию плюс CHECK - существующие данные не меняются, риск минимальный (по правилу из бэклога «Проверка миграций на данных до выкатки»); тест на временной базе обязателен по `CHECKED_MIGRATIONS`
- `birth_congratulated_on` дописывается в ту же `0004`: она ещё нигде не выкатывалась. Локальная база, где `0004` уже применена, пересоздаётся (миграции заново, сид) - по согласию владельца
- Выкатка обычная: тест-стенд → прод (бэкап → миграции → образ → smoke)
- Откат - Deploy prod с галочкой «откат»: старый образ не читает новые столбцы и работает с ними; столбцы остаются в базе
