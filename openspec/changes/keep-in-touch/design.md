# Design

## Context

Мотивация - `proposal.md`, поведение - `specs/keep-in-touch/spec.md`.

Сейчас: `contacts` (без полей ритма) и `notes` с `created_at` и индексом `(contact_id, created_at)`. Весь доступ к данным - `src/server/contacts.ts`; формы - server actions в `src/app/contacts/actions.ts`, работают без JavaScript (e2e шлёт формы как браузер без JS). Валидация - zod в `src/lib/validation.ts`. Контактов порядка тысячи (замеры в `specs/backlog.md`).

## Goals / Non-Goals

**Goals:**
- Один источник правды для расчёта срока и статуса, покрытый юнит-тестами без базы
- Блок и точки в списке без N+1 запросов
- Всё, что меняет данные, работает без JavaScript; переключение и листание блока - без перезагрузки и запросов к серверу

**Non-Goals:**
- Дата общения задним числом в заметке (отложено владельцем)
- Удаление заметок и отмена «Связались»
- Уведомления (вне продукта, см. `specs/01-продуктовая-идея.md`)

## Decisions

### 1. Модель данных: два столбца в `contacts`

- `cadence` - Postgres enum `contact_cadence`: `week`, `month`, `quarter`, `half_year`, `year`, `date`; `NULL` = «Не задано»
- `contact_on` - `date`, заполнен только при `cadence = 'date'`
- `CHECK (coalesce(cadence = 'date', false) = (contact_on IS NOT NULL))` - период и дата не смешиваются на уровне базы. `coalesce` нужен: при `cadence = NULL` простое сравнение даёт NULL, а CHECK пропускает NULL, и дата без частоты прошла бы

Последнее общение не храним: это `max(notes.created_at)`, иначе `coalesce(..., contacts.created_at)`. Отдельный столбец `last_contacted_at` пришлось бы синхронизировать при каждой заметке, а индекс по заметкам уже есть.

Альтернатива: `cadence_days int`. Отклонена: месяцы календарные, в днях не выражаются.

### 2. Расчёт срока и статуса - чистые функции в `src/lib/keep-in-touch.ts`

`dueDate(cadence, lastContact, contactOn)`, `status(due, today, cadence)` → `{ kind: 'overdue' | 'soon' | 'ok', days }`, `sortForReminders`, `pluralDays`. Календарная арифметика на датах без времени (`YYYY-MM-DD`): добавление месяцев с прижатием к последнему дню месяца. Сегодня и дата последнего общения переводятся в дату через `Intl.DateTimeFormat` с часовым поясом `APP_TIME_ZONE` (константа, по умолчанию `Europe/Moscow`).

Почему не SQL: правила (окна, конец месяца, склонения) проще тестировать в TS. Почему без библиотеки дат: нужно только «+N месяцев с прижатием», это десяток строк; новая зависимость не окупается.

### 3. Запросы: один запрос на всех контактов с частотой

`listReminders()` - `contacts` с `cadence IS NOT NULL` + `left join` агрегата `max(created_at)` по заметкам, без лимита (их немного; при 1000 контактах - один быстрый запрос по индексу). Статус, фильтр и сортировка - в TS функциями из п.2. Отдельно `count(*)` контактов с частотой и всех контактов - для пустых состояний.

`listContacts()` дополняется теми же полями для текущей страницы (50 строк) - статус для точек считается той же функцией.

Альтернатива: считать срок и сортировать в SQL. Отклонена: дублирование правил в двух местах.

### 4. Снятие конкретной даты - в `addNote`, в транзакции

`addNote` в одной транзакции вставляет заметку и, если `cadence = 'date'` и статус по п.2 «скоро» или «просрочено» на момент вставки, ставит `cadence = NULL, contact_on = NULL`. «Связались» вызывает тот же `addNote` с текстом «Связались» - правило одно для обоих путей. `updateNote` не трогаем.

### 5. Формы и действия

- В `contactSchema` - поля `cadence` (строка из списка или пусто) и `contactOn`; `superRefine`: при `date` дата обязательна, иначе `contactOn` сбрасывается в `null`
- Проверка «не раньше сегодня» (по `APP_TIME_ZONE`) - только для новой или изменённой даты. Схема строится функцией с параметром `savedContactOn` (дата, сохранённая у контакта): при создании - `null`, при правке и смене частоты в карточке действие сначала читает контакт. Дата, равная сохранённой, проходит, даже если прошла - иначе просроченную дату нельзя было бы пронести через правку телефона
- Поле в `ContactForm` - нативный `<select>` плюс `<input type="date">`, который показывается при «Конкретная дата». Без JS дата видна всегда, сервер её игнорирует, если выбран не `date`
- Смена частоты в карточке - отдельная маленькая форма `setCadenceAction` с кнопкой «Сохранить» (без JS) - вид решит эскиз
- «Связались» - форма с hidden `contactId` и `returnTo` (`/` или карточка), `markContactedAction` → `revalidatePath` для `/` и карточки. Без JS - `redirect` обратно; с JS - форма через `useActionState`, без перехода: страница обновляется данными сервера, а состояние блока (раскрыт, номер страницы) живёт в клиентском компоненте и сохраняется. Если текущая страница блока опустела - номер страницы прижимается к последней

### 5a. Блок «Пора связаться» - клиентский компонент над предзагруженными строками

Сервер отдаёт в разметке все строки блока (`listReminders()` без лимита, п.3). `RemindersBlock` (client component) держит `expanded` и `page`: свёрнутый - первые 5, раскрытый - срез по 10, пагинация - кнопки по образцу `PageArrow` общего списка, но `<button>`, не ссылки. «Показать все (N)» и «Свернуть» - `<button type="button">`, `aria-expanded` на кнопке раскрытия. Ни сворачивание, ни листание не трогают адрес и сервер.

После «Связались» сервер присылает новый список строк, а компонент выводит вид из него, а не из старого состояния: при 5 строках и меньше `expanded` сбрасывается, кнопок и пагинации нет; при 0 строк - «Со всеми на связи» (пустое состояние рендерит тот же компонент, а не страница, чтобы смена шла без перезагрузки).

Без JS: сервер рендерит все строки, а лишние строки и кнопки скрывает CSS только при `<html data-js>`. Атрибут ставит крошечный inline-скрипт в `<head>` до первой отрисовки - нет вспышки «все строки → 5» при гидрации. Без JS атрибута нет: видны все строки, кнопок нет.

Альтернативы: `<details>` или чекбокс с `:has()` - работают без JS, но пагинацию на CSS не сделать; пагинация через адрес (`?remindersPage=2`) - перезагрузка на каждое листание, против решения владельца.

### 6. Дизайн - по утверждённым эскизам

Эскизы и решения 14–20 в `design/README.md` утверждены владельцем; экраны в коде повторяют их. Правило дизайн-системы «одна пульсирующая точка на страницу» осознанно нарушено (решение 15). Точка «просрочено» - новый токен приложения `--overdue` `#d9622b`: в дизайн-системе его нет, заводится по правилам `src/design-system/README.md` («App tokens»).

## Risks / Trade-offs

- [Случайное нажатие «Связались» создаёт заметку, удалить её нельзя] → её можно отредактировать; удаление заметок - кандидат в бэклог
- [Часовой пояс зашит константой] → один владелец, один пояс; смена - правка константы
- [«Скоро» для конкретной даты: заметка за 8 дней до даты дату не снимет] → это правило спеки; если неудобно - поменять окно
- [Расчёт в TS требует выбрать всех контактов с частотой] → сотни строк, приемлемо; при росте - перенести фильтр в SQL

## Migration Plan

Миграция только добавляет enum, два nullable-столбца и CHECK - существующие строки остаются валидными (`NULL`, `NULL`). Выкатка обычная: миграция разовым контейнером → новый образ → smoke `/health`. Откат образа на предыдущий безопасен: старый код не читает новые столбцы.
