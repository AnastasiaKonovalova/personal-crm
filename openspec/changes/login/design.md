# Design

## Context

- Пользователей нет. Все функции доступа к данным (`src/server/contacts.ts`, `src/server/groups.ts`) читают и пишут всю базу. Страницы и server actions вызывают их напрямую
- Таблицы: `contacts`, `notes` (каскад от контакта), `groups` (уникальный индекс по `lower(translate(name, 'Ёё', 'Ее'))` на всю базу), `contact_groups`
- Формы работают и без JavaScript: id передаются скрытыми полями, без `.bind()`, а для POST без JS делается redirect. Новые формы (вход, «Выйти») должны вести себя так же
- Миграции применяет `src/db/migrate.ts`: на сервере это разовый контейнер перед стартом приложения, локально сейчас `drizzle-kit migrate`. Каждая миграция обязана иметь свою проверку в `tests/migration-on-data.test.ts`
- e2e: HTTP-тесты (`tests/e2e/*.e2e.ts`, `fetch` без cookie) и браузерные (`tests/browser/*.spec.ts`) против запущенного приложения. Главный сценарий считает «Всего» по всей таблице `contacts`
- Сервер маленький: у контейнера `app` лимит 256 МБ
- Репо публичное: почта владельца не должна попасть в код или миграции

## Goals / Non-Goals

**Goals:**
- Изоляция данных задаётся на уровне типов: функция доступа к данным без `userId` не компилируется
- Вход и правила ссылки проверяются на сервере в одном месте, общем для нашей формы и прямого запроса к API Better Auth
- Существующие данные переходят к владельцу одной атомарной миграцией. Если с почтой владельца что-то не так, миграция падает, а не создаёт данные без владельца

**Non-Goals:**
- Ограничение частоты запросов по IP и защита от перебора с многих почт. Лимит в спеке только на почту; встроенный лимит Better Auth по IP оставляем по умолчанию (в e2e против production-сборки он выключен, решение 2а)
- Удаление пользователя и его данных. Внешние ключи на пользователя ставим `RESTRICT`, а не каскад
- Проверка владельца на уровне базы (RLS, составные внешние ключи)

## Decisions

### 1. Better Auth: таблицы и настройки

- Better Auth с адаптером Drizzle (`better-auth/adapters/drizzle`) и плагинами `magicLink` и `nextCookies` (без него cookie из server actions не ставятся)
- Таблицы Better Auth описываем в `src/db/schema.ts` во множественном числе, как наши: `users`, `sessions`, `accounts`, `verifications` (`modelName` в конфиге). Колонки — по схеме установленной версии: генерируем через CLI Better Auth и сверяем. Альтернатива — имена по умолчанию (`user` — зарезервированное слово Postgres, придётся всюду брать в кавычки). Отклонена
- `magicLink({ expiresIn: 900, disableSignUp: false })`: первый вход создаёт пользователя, имя пустое
- Сессия: `expiresIn` 30 дней, `updateAge` 1 день — срок продлевается при заходе не чаще раза в сутки. Получается «30 дней с последнего захода» с точностью до суток. `cookieCache` выключен: выход и истечение действуют сразу
- Маршрут `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`): по нему переходят по ссылке из письма и работает API Better Auth
- `callbackURL: "/"`, `errorCallbackURL: "/login/expired"`: при устаревшей, использованной или погашенной ссылке Better Auth уводит на экран «Ссылка устарела»

### 2. Правила почты и лимит — в before-хуке Better Auth

Нормализация (`trim` + `toLowerCase`), проверка формата (та же zod-схема, что у формы) и лимит 3 письма за 10 минут выполняются в `hooks.before` для пути `/sign-in/magic-link`. Хук подменяет почту в теле запроса на нормализованную, а при ошибке бросает `APIError` с кодом. Наша server action формы входа вызывает `auth.api.signInMagicLink` и переводит код ошибки в текст: «Проверь адрес почты» или «Слишком часто, попробуй через несколько минут».

Альтернатива — проверки только в server action. Отклонена: эндпоинт Better Auth открыт, и прямой запрос прошёл бы мимо проверок (спека: «даже если запрос пришёл не из формы»).

Проверено по коду better-auth 1.7.25 (задача 1.3, `dist/api/dispatch.mjs`):
- `hooks.before` вызывается и для HTTP-запроса, и для `auth.api.*`, до проверки тела схемой эндпоинта. Хук возвращает `{ context: { body: { ...ctx.body, email } } }`, и это тело заменяет исходное (`defu`: значения хука главнее). Бросок `APIError` из хука уходит наружу как ошибка запроса. Хук видит сырое тело: `ctx.body` может быть не объектом, это проверяем сами
- Встроенный лимит по IP (`rateLimit` плагина, 5 запросов за 60 с, включён по умолчанию только в production) работает в HTTP-роутере и не применяется к вызовам `auth.api` из server action. Для формы действует только наш лимит по почте (решение 3); встроенный страхует прямые запросы к `/api/auth`
- Проверка CSRF (`formCsrfMiddleware`) срабатывает только когда есть `ctx.request`, то есть для HTTP-запросов; вызов `auth.api.signInMagicLink` из server action её пропускает. Заголовки в вызов всё равно передаём (`requireHeaders: true`)
- `callbackURL` и `errorCallbackURL` из тела проходят `originCheck` по доверенным origin; `errorCallbackURL`, если его не передать, заменяется на `callbackURL`. Поэтому server action всегда передаёт `callbackURL: "/"` и `errorCallbackURL: "/login/expired"`. Решение владельца (2026-11-17): те же значения принудительно ставит `hooks.before` и для прямых запросов к API, а `callbackURL`, `newUserCallbackURL`, `errorCallbackURL`, `name` и `metadata` из тела запроса отбрасываются

### 2а. Встроенный лимит Better Auth по IP в e2e

Найдено в 8.1 (`scripts/checks.sh`, 2026-11-19): плагин magicLink ставит лимит 5 запросов за 60 с с одного IP на `/sign-in/magic-link` и `/magic-link/verify` (`dist/plugins/magic-link/index.mjs`), а Better Auth включает лимиты только в production (`rateLimit.enabled ?? isProduction`, `dist/context/create-context.mjs`). e2e до этого шли против `pnpm dev`, где лимита нет. Против production-сборки (CI, `checks.sh`) все запросы идут с одного адреса: около 32 открытий ссылки за прогон, после пятого вход не происходит.

Решение владельца (2026-11-19): переменная `E2E_AUTH_IP_LIMIT=off` передаёт Better Auth `rateLimit: { enabled: false }`. Её ставят только `ci.yml` (job `e2e`) и `scripts/checks.sh`. Без переменной и при любом другом значении настройка не передаётся, и на сервере действует умолчание Better Auth. Наш лимит 3 письма за 10 минут на почту (решение 3) от переменной не зависит и проверяется в e2e.

Отклонено: поднять лимит для всех (ослабляет защиту на проде); разный `X-Forwarded-For` в тестах (тесты опирались бы на подделку адреса); паузы в тестах (прогон дольше на 8 минут и больше); общие пользователи в тестах входа (останется 15–17 открытий, всё равно больше 5 в минуту).

### 3. Лимит писем — своя таблица

`login_emails (id, email, sent_at)`, индекс `(email, sent_at)`. Хук считает строки этой почты за последние 10 минут: 3 и больше — отказ. Строка пишется после успешной отправки письма в `sendMagicLink`. Старые строки (старше суток) удаляются при той же записи.

Альтернатива — встроенный `rateLimit` Better Auth. Отклонена: он считает по IP и пути, а не по почте, и по умолчанию хранит счётчики в памяти процесса.

### 4. Новая ссылка гасит старые

Плагин сам удаляет запись `verifications` после успешного входа, поэтому ссылка одноразовая. Гашение прежних ссылок делаем сами: в `sendMagicLink` перед отправкой удаляем другие записи `verifications` этой почты (почта лежит в `value`, токен — в `identifier`). Как именно хранятся `value` и `identifier` в установленной версии, проверяем при реализации (см. Risks).

Проверено по коду better-auth 1.7.25 (задача 1.3, `dist/plugins/magic-link/index.mjs`):
- `storeToken` по умолчанию `plain`, `verification.storeIdentifier` не задан (значит `plain`): токен в базе хранится открытым, `identifier = "magic-link:<токен>"`, `value = {"type":"magic-link","email":"<почта>"}` (JSON-строка; `name` не попадает, если не передан)
- Гашение прежних ссылок: в `sendMagicLink` (запись текущей ссылки уже создана, её токен приходит аргументом `token`) своим запросом Drizzle удаляем из `verifications` строки с `identifier LIKE 'magic-link:%'`, `identifier <> 'magic-link:' || <token>` и `value = <та же JSON-строка для этой почты>`. Сравнение по точной строке: тест «Запросил новую ссылку» поймает смену формата
- Одноразовость: плагин потребляет токен атомарно (`consumeVerificationValue`); использованная, просроченная, погашенная и несуществующая ссылки одинаково ведут на `errorCallbackURL?error=INVALID_TOKEN`. Один экран `/login/expired` покрывает все случаи
- Просроченные строки `verifications` Better Auth сам чистит раз в интервал при чтении; свои ссылки без чистки не копятся
- `expiresIn` по умолчанию 300 с: задаём 900 явно

### 5. Письма: Nodemailer поверх SMTP

`src/server/mail.ts`: транспорт Nodemailer из переменных `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD` и отправитель `MAIL_FROM` (`"Свои люди - Личная CRM" <noreply@mail.crm.<домен>>`).

- Локально и в CI: Mailpit, SMTP `localhost:1025`, без логина
- На сервере: SMTP Resend (`smtp.resend.com:465`, пользователь `resend`, пароль — ключ Resend)

Код один для всех окружений; транспорт создаётся при первой отправке, не при импорте, чтобы сборка не требовала настроек. Письмо в двух видах, HTML и текст: кнопка «Войти», срок 15 минут, фраза про игнорирование. Почту получателя в логи не пишем.

Альтернатива — SDK Resend. Отклонена: спека требует одну библиотеку Nodemailer для всех окружений, а SMTP Resend это позволяет без отдельного клиента.

### 6. Текущий пользователь: `requireUser()` в каждой точке входа

`src/server/session.ts`: `getCurrentUser()` (сессия через `auth.api.getSession({ headers })` или `null`) и `requireUser()`, которая без сессии делает `redirect("/login")`. Вызывается первой строкой в каждой странице (кроме `/login`, `/login/expired`, `/health`) и в каждой server action.

Все функции `src/server/contacts.ts` и `src/server/groups.ts` получают `userId` первым обязательным аргументом. Каждый запрос фильтрует `contacts.user_id = userId` или `groups.user_id = userId`. Запись чужого пользователя для функции не существует: возвращается `null` или `false`, как сейчас для удалённой. Заметки и членства проверяются через контакт: `addNote`, `updateNote` и членства сначала находят контакт с этим `userId`. `existingGroupIds`, `findGroup` и `findOrCreateGroupIn` ищут только группы этого пользователя, поэтому отметка чужой группы молча отбрасывается, как удалённая.

Альтернатива — проверка в `layout.tsx` или в `proxy.ts`. Отклонена как единственная защита: layout не защищает server actions и не перезапускается при каждой навигации, а proxy видит только наличие cookie. Позже `proxy.ts` можно добавить ради быстрого redirect, но он ничего не заменяет.

### 6а. Продление cookie сессии — в `src/proxy.ts`

Найдено в 7.2 (тест «Заход продлевает вход», 2026-11-19): сессию читают серверные компоненты (`getCurrentUser()`), а в них Next запрещает ставить cookie. При заходе Better Auth продлевает `sessions.expires_at` в базе и пытается поставить cookie с новым `Max-Age`; `nextCookies` молча проглатывает ошибку (`better-auth/dist/integrations/next-js.mjs`), а при навигации RSC продление пропускает совсем. Итог: браузер выбрасывает cookie через 30 дней после входа, даже если человек заходил каждый день. Срок cookie настройкой не продлить: `setSessionCookie` ставит `maxAge` поверх атрибутов из `advanced.cookies`.

Решение владельца (2026-11-19): `src/proxy.ts` на запросах страниц с cookie сессии вызывает `getAuth().api.getSession({ headers, returnHeaders: true })` и переносит его `Set-Cookie` в ответ. Продление по-прежнему не чаще раза в сутки (`updateAge`). Доступ proxy не проверяет и ничего не заменяет: `requireUser()` остаётся в каждой странице и action (решение 6). Цена — одно лишнее чтение сессии из базы на запрос страницы. При реализации проверить по `node_modules/next/dist/docs/` среду выполнения proxy (Node.js нужен для `pg`) и `matcher` (без `/api`, `/_next`, `/health`, статики).

Отклонено: «30 дней с момента входа» (меняет спеку, вход раз в месяц при ежедневной работе); скрипт в браузере, дёргающий `/api/auth/get-session` (без JS не работает).

### 7. Модель данных

- `contacts.user_id`, `groups.user_id`: `text NOT NULL`, внешний ключ на `users.id` с `ON DELETE RESTRICT`, индекс по `user_id`
- Уникальный индекс групп: `(user_id, lower(translate(name, 'Ёё', 'Ее')))` вместо глобального; `findOrCreateGroupIn` ищет с тем же `user_id`
- `notes` и `contact_groups` без `user_id`: владелец берётся от контакта (спека: «заметки принадлежат владельцу контакта»)
- `users.email` уникален. Better Auth хранит почту в нижнем регистре, а наш хук гарантирует `trim`

### 8. Перенос существующих данных — одна SQL-миграция с почтой владельца из настройки соединения

Миграция `0003`, в одной транзакции:
1. создаёт таблицы Better Auth и `login_emails`, добавляет `user_id` (пока NULL)
2. если в `contacts` или `groups` есть строки, читает почту владельца из `current_setting('app.owner_email', true)`. Пусто — `RAISE EXCEPTION`: миграция падает, и новый образ не стартует (так уже устроена выкатка)
3. создаёт пользователя с `lower(trim(почта))`, если его нет, и проставляет его `id` всем строкам `contacts` и `groups`
4. ставит `NOT NULL`, внешние ключи и новый уникальный индекс групп, удаляет старый

`src/db/migrate.ts` передаёт настройку через `options: "-c app.owner_email=..."` из переменной `OWNER_EMAIL`. Чтобы локально и на сервере миграции шли одним путём, `pnpm db:migrate` начинает вызывать `src/db/migrate.ts` (как на сервере) вместо `drizzle-kit migrate`. На пустой базе (CI) почта не нужна. Почта в git не попадает: она лежит в `.env` локально и на сервере.

Источник почты решён владельцем 2026-11-15: переменная `OWNER_EMAIL`. Значение владелец сам записывает в `.env` на этапе реализации (локально и на сервере). Отклонённые варианты:
- (б) почта в самом SQL — отклонено: репо публичное
- (в) «бесхозные» записи забирает первый вошедший пользователь — отклонено: проиграть гонку может кто угодно, а пока никто не вошёл, данные остаются без владельца, и `NOT NULL` поставить нельзя
- (г) отдельный скрипт после миграций — отклонено: две миграции и шаг между ними в разных транзакциях, и на время между ними `NOT NULL` нет

### 9. Сид

`src/db/seed.ts` находит или создаёт пользователя `OWNER_EMAIL` (без переменной — понятная ошибка) и создаёт демо-контакты и группы у него. «Таблица уже заполнена — пропустить» теперь считается по этому пользователю.

### 10. Экраны

- `/login`: форма почты (server action, работает без JS). Состояния: исходное, ошибка под полем, «Ссылка для входа отправлена на <почта>», «Слишком часто…». Вошедшего пользователя `/login` уводит на `/`
- `/login/expired`: «Ссылка устарела, запроси новую» и кнопка на `/login`
- Шапка в `layout.tsx`: при сессии справа почта (длинная обрезается многоточием) и форма «Выйти» (server action → `auth.api.signOut` → redirect `/login`, без JS тоже работает)
- `EmptyList`: без контактов совсем, без поиска и группы — подсказка «Добавь первый контакт»
- Вид — по эскизам в `design/` до кода экранов, как в прошлых фичах; ширины 1280, 900, 390

### 11. Тесты

- Интеграционные (Vitest): помощник `createTestUser()` создаёт пользователя напрямую в `users` (это данные, которые тест готовит сам) и удаляет его вместе с его данными. Существующие тесты переходят на своего пользователя. Новый `tests/ownership-scenario.test.ts`: A и B на каждую функцию из `src/server` — чтение, правка, удаление, заметки, «Связались», частота, группы и членства
- HTTP e2e: помощник `tests/e2e/auth.ts` запрашивает ссылку, берёт письмо из Mailpit API (`/api/v1/search?query=to:<почта>`), открывает ссылку и возвращает cookie сессии. `getPage` и `submitForm` принимают cookie. Новый `tests/e2e/login.e2e.ts`: нормализация, проверка почты мимо формы, лимит, одноразовость, гашение старых ссылок, срок 15 минут (тест сдвигает `expires_at` своей записи `verifications` в базе), сессия 30 дней и продление (тест сдвигает `expires_at` и `updated_at` своей сессии), два устройства, выход на одном устройстве, `/health` без входа, редиректы без входа, POST без входа
- Браузерный `tests/browser/login.spec.ts`: главный сценарий спеки, A и B. `main-scenario.spec.ts` и `keep-in-touch.spec.ts` перед сценарием входят под своим пользователем, а «Всего» считают по его контактам
- Почты в тестах выдуманные и уникальные: `<marker>@example.test`. Тест удаляет свои письма из Mailpit и своих пользователей
- Каждый сценарий спеки — свой тест (правило `openspec/config.yaml`); сводка покрытия — `coverage.md`, как в прошлых фичах

### 12. Окружения

- `docker-compose.yml`: сервис `mailpit` (закреплённая версия образа `axllent/mailpit`), порты `127.0.0.1:1025` и `127.0.0.1:8025`
- `.env.example`: `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM`, `OWNER_EMAIL` — без значений
- CI: сервис Mailpit в jobs `unit` и `e2e`. Одноразовые значения `BETTER_AUTH_SECRET` и `BETTER_AUTH_URL=http://localhost:3000` прямо в workflow — это не секреты, база и приложение живут один прогон
- `deploy/compose.yml`: новые переменные в `app` (из `.env` сервера), `OWNER_EMAIL` в `migrate`. Строки в `.env` на сервере добавляет владелец

## Risks / Trade-offs

- [Устройство `verifications` в установленной версии Better Auth (хеширование токена, формат `value`) может не дать удалить старые ссылки по почте] → **подтверждён** (1.3): токен и почта хранятся открытым текстом, прежние ссылки находятся по `value` (решение 4). Запасная таблица «почта → токен» не нужна
- [before-хук может не дать подменить тело запроса] → **подтверждён** (1.3): хук подменяет тело запроса и бросает `APIError` (решение 2). Запасной путь не нужен
- [Неверная или пустая `OWNER_EMAIL` на сервере] → пустая роняет миграцию до старта образа, данные не тронуты. Опечатка отдаст данные пользователю с неверной почтой: перед выкаткой владелец сверяет строку в `.env`, после выкатки — входит и видит свои контакты; исправляется одним `UPDATE users SET email` по согласованию
- [На проде не уходят письма: домен в Resend не подтверждён или нет ключа] → владелец не войдёт в свою CRM. Подтвердить домен и проверить ключ до merge; после выкатки сразу проверить вход
- [Better Auth читает секрет и URL при импорте и ломает `pnpm build` в CI без переменных] → **риск реален, нужен запасной путь** (1.3): `betterAuth()` запускает инициализацию контекста сразу при вызове, а без `BETTER_AUTH_SECRET` в production она бросает ошибку (`create-context.mjs`). Поэтому `src/server/auth.ts` экспортирует `getAuth()`: `betterAuth()` создаётся при первом вызове и запоминается; route handler и `session.ts` вызывают `getAuth()` внутри обработчика, не на уровне модуля. Route handlers в Next.js по умолчанию не кэшируются и при сборке не выполняются, но сам модуль при сборке импортируется, поэтому вызова на верхнем уровне быть не должно. Проверка — `pnpm build` без переменных в задаче 5.3 и сборка образа в CI
- [Память: Better Auth и Nodemailer увеличат потребление в контейнере с лимитом 256 МБ] → после выкатки посмотреть `docker stats`
- [Откат после этой выкатки сложнее обычного: `rollback.sh` вернёт старый образ, а он не умеет писать в схему с `NOT NULL user_id`] → откат только вместе: restore из бэкапа, снятого `deploy.sh` перед миграцией, и прошлая версия. Порядок — в README
- [Продление сессии раз в сутки: «30 дней с последнего захода» точно только до суток] → принятое упрощение, записано здесь

## Migration Plan

1. До merge: владелец подтверждает домен `mail.crm.<домен>` в Resend (записи DNS), создаёт ключ Resend и добавляет строки в `.env` на сервере (агент скажет какие, в том числе `OWNER_EMAIL`)
2. Миграцию `0003` и её проверку на данных показать владельцу до merge (правило `AGENTS.md`)
3. Merge → обычная выкатка: бэкап → миграции (перенос данных) → новый образ → smoke `/health`
4. Проверка: владелец входит под своей почтой (письмо приходит), видит все прежние контакты, группы и заметки. Числа строк в `contacts`, `notes`, `groups`, `contact_groups` совпадают с бэкапом. Вход с другой почты показывает пустой список
5. Откат — только вручную и только вместе, порядок ниже. В README его переносит задача 8.3

### Откат выкатки входа

Запускает владелец. Шаги на сервере:

1. `ssh vps_hostkey`, затем `sudo -u crm-deploy ls -l /opt/personal-crm/backups/`. Нужен бэкап этой выкатки: `<время>-<SHA прошлой версии>.dump`, его снял `deploy.sh` до миграции `0003`. Файлы `*-pre-restore.dump` не подходят
2. `sudo -u crm-deploy /opt/personal-crm/rollback.sh` — вернуть прошлую версию приложения. Сначала версия, потом база (README, «Версии»). До шага 3 прошлая версия не может сохранять контакты и группы: схема уже новая
3. `sudo -u crm-deploy /opt/personal-crm/restore.sh /opt/personal-crm/backups/<файл из шага 1>.dump`, подтвердить `yes`
4. Проверка: `https://app.mypeoplecrm.ru/health` отвечает 200; приложение открывается без входа и показывает данные на момент бэкапа

Что важно знать:
- Всё, что любой пользователь (владелец и друзья) создал или изменил после выкатки, пропадёт: база возвращается к состоянию до выкатки. Копию базы перед восстановлением `restore.sh` снимает сам (`*-pre-restore.dump`)
- Отдельно один `rollback.sh` не работает: старая версия не умеет писать в схему с `user_id NOT NULL`. Отдельно один `restore.sh` тоже нет: новая версия не запустится на старой схеме
- Пока вход остаётся в main, следующая выкатка из main снова применит миграцию `0003` к восстановленной базе. Чтобы этого не было, вход нужно откатить и в main (revert PR)

## Решённые вопросы (владелец, 2026-11-15)
