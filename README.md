# Свои люди

«Свои люди» — личная CRM для контактов людей, которых знаю лично: кто это, откуда знакомы, телефон и почта, заметки о разговорах. Идея и главный сценарий — в `specs/01-продуктовая-идея.md`.

## Стек

Next.js (App Router) + TypeScript, React, Tailwind CSS, shadcn/ui, PostgreSQL в Docker, Drizzle ORM (схема — `src/db/schema.ts`, миграции — `drizzle/`), pnpm. К базе обращается только сервер: страницы — серверные компоненты, изменения — Server Actions.

Вход — Better Auth, по ссылке из письма (паролей нет). Письма отправляет Nodemailer: локально и в автотестах — в почтовую заглушку Mailpit, на сервере — через Resend. Каждый пользователь видит только свои контакты, заметки и группы.

## Требования

- Docker Desktop (запущен)
- Node.js 24 (версия в `.nvmrc`)
- pnpm

## Первый запуск

1. Создай файл с настройками из шаблона:
   ```bash
   cp .env.example .env
   ```
2. Заполни в `.env` значения `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` и `DATABASE_URL`.
   Пароль можно сгенерировать командой `openssl rand -hex 24`.
   Для входа и писем впиши (локально письма уходят в Mailpit, логин не нужен):
   ```
   BETTER_AUTH_SECRET=<вывод команды openssl rand -hex 32>
   BETTER_AUTH_URL=http://localhost:3000
   SMTP_HOST=localhost
   SMTP_PORT=1025
   SMTP_SECURE=false
   SMTP_USER=
   SMTP_PASSWORD=
   MAIL_FROM='"Свои люди - Личная CRM" <noreply@example.test>'
   OWNER_EMAIL=<твоя почта>
   ```
   `MAIL_FROM` — целиком в одинарных кавычках, иначе `docker compose` не прочитает `.env`. `OWNER_EMAIL` — пользователь, у которого сид создаёт демо-данные; под этой почтой ты их увидишь.
3. Запусти базу и почтовую заглушку Mailpit:
   ```bash
   docker compose up -d
   ```
4. Установи зависимости:
   ```bash
   pnpm install
   ```
5. Создай таблицы:
   ```bash
   pnpm db:migrate
   ```
6. Заполни базу тестовыми данными — 1000 вымышленных контактов с заметками:
   ```bash
   pnpm db:seed
   ```
   Сид срабатывает только на пустой базе: если контакты уже есть, он ничего не делает.
7. Запусти приложение:
   ```bash
   pnpm dev
   ```
   и открой http://localhost:3000 — откроется страница входа.
8. Войди под почтой из `OWNER_EMAIL`: впиши её, нажми «Получить ссылку», открой письмо в Mailpit (http://localhost:8025) и нажми «Войти». Подробнее — «Вход и почта локально».

## Вход и почта локально (Mailpit)

Mailpit поднимается вместе с базой (`docker compose up -d`). Настоящих писем он не отправляет: все письма приложения попадают к нему, его страница — http://localhost:8025. Письма хранятся в памяти и пропадают после перезапуска контейнера.

**Войти:**
1. На http://localhost:3000 впиши почту и нажми «Получить ссылку» — «Ссылка для входа отправлена на <почта>».
2. В Mailpit открой письмо «Ссылка для входа в «Свои люди»» и нажми «Войти» — откроется список контактов.
3. Ссылка работает 15 минут и один раз; новая ссылка гасит прежние. Старая ссылка открывает «Ссылка устарела, запроси новую».
4. Не больше 3 писем на одну почту за 10 минут, дальше — «Слишком часто, попробуй через несколько минут».
5. Выйти — «Выйти» в шапке справа (выход только на этом устройстве).

**Под любой почтой.** Ящик не нужен: письмо всё равно придёт в Mailpit. Первый вход с новой почтой создаёт пользователя с пустым списком («Добавь первый контакт»). Так проверяются два пользователя: второго открой в другом браузере или в приватном окне — его контактов первый не видит, и наоборот. Почты бери выдуманные, например `anna@example.com`.

## Режимы запуска

**Разработка** — изменения в коде подхватываются сразу, страницы собираются при первом открытии:
```bash
pnpm dev
```

**Продакшен** — собранная оптимизированная версия, работает быстрее. После каждого изменения кода её нужно пересобрать:
```bash
pnpm build
pnpm start
```

В обоих случаях приложение открывается на http://localhost:3000. Остановить сервер — `Ctrl+C` в терминале, где он запущен. Одновременно может работать только один из них: оба занимают порт 3000.

## Проверки

```bash
pnpm lint          # ESLint
pnpm format:check  # формат кода (Prettier); исправить — pnpm format
pnpm typecheck   # проверка типов
pnpm test        # тесты: валидация и главный сценарий на настоящей базе
pnpm build       # продакшен-сборка
pnpm test:e2e    # критерии успеха через HTTP, затем главный сценарий в браузере (Playwright) — нужно запущенное приложение (см. ниже)
```

Для `pnpm test:e2e` запусти приложение так:
```bash
pnpm build
E2E_AUTH_IP_LIMIT=off pnpm start
```
Better Auth в продакшен-режиме пускает не больше 5 запросов входа в минуту с одного адреса, а все тесты идут с твоего компьютера — без `E2E_AUTH_IP_LIMIT=off` вход в тестах перестаёт работать. Переменная действует только на этот запуск; на сервере её нет. Против `pnpm dev` тесты идут и без неё: там этого лимита нет.

Перед первым `pnpm test:e2e` на машине один раз скачай браузер для Playwright (около 300 МБ, в `~/Library/Caches/ms-playwright`, не в репо):
```bash
pnpm exec playwright install chromium
```
Посмотреть браузерный тест в открытом окне: `pnpm exec playwright test --headed`. Если упал — отчёт и трасса в `test-results/`, открыть трассу: `pnpm exec playwright show-trace test-results/<папка>/trace.zip`. Браузерные тесты запускаются, только если прошли HTTP-тесты.

Тестам нужны запущенные база и Mailpit. Каждый тест входит под своим выдуманным пользователем (`…@example.test`) и в конце удаляет его вместе с его данными и письмами. `pnpm test` создаёт один контакт «Тестовый Контакт …», `pnpm test:e2e` — «Проверка Сквозная …», 51 контакт «Пагинация Проверка …» (для проверки страниц) и «Проверка Браузерная …»; в конце каждый удаляет только свои контакты.

На каждый PR в main те же проверки гоняет CI (`.github/workflows/ci.yml`): lint, формат и типы, Vitest, e2e (HTTP и Playwright) на временной базе, сборка образа без публикации. Красный CI в main не вливается. При выкатке `deploy.yml` запускает этот же `ci.yml`, поэтому проверки на PR и перед выкаткой одни и те же.

## Ручная проверка критериев успеха

Сначала войди под почтой из `OWNER_EMAIL` («Вход и почта локально»): демо-данные сида принадлежат этому пользователю.

1. **Список всех контактов.** Открой http://localhost:3000 — вверху «Всего: 1000», ниже список по алфавиту, по 50 на страницу, внизу «Страница 1 из 20» между круглыми стрелками. Левая стрелка («Назад») на первой странице бледная и не нажимается, правая («Вперёд») открывает вторую страницу. Вся строка контакта кликабельна и открывает карточку.
2. **Добавил → нашёл → дописал заметку.**
   - Нажми «Добавить контакт», заполни имя (например, «Проверка Ручная»), сохрани — откроется карточка нового контакта.
   - Вернись к списку («Все контакты»), введи в поиск часть имени в любом регистре («ручн») — контакт найдётся.
   - Открой карточку, напиши заметку, нажми «Добавить заметку» — она появится в ленте с датой.
   - Обнови страницу (Cmd+R) — заметка на месте.
3. **Другой браузер.** Открой тот же адрес карточки в другом браузере (например, Safari, если до этого был Chrome) и войди там под той же почтой — там те же контакт и заметка. Данные лежат в базе, а не в браузере.
4. **Поиск по «е» и «ё».** Создай контакт «Фёдоров Проверка». Поиск «федоров» и «фёдоров» находит его в обоих случаях, и наоборот: имя с «е» находится запросом с «ё».
5. **Редактирование контакта.** На карточке нажми «Редактировать» — форма заполнена текущими данными. Сотри имя и сохрани — под полем «Имя обязательно». Впиши новые данные и сохрани — откроется карточка с ними, в списке новое имя. «Отмена» возвращает на карточку без изменений.
6. **Редактирование заметки.** У заметки нажми «Изменить», поправь текст, нажми «Сохранить» — текст обновится, дата останется прежней. Пустой текст не сохраняется: «Заметка пустая». Обнови страницу — правка на месте.
7. **Удаление контакта.** На карточке нажми «Удалить» — откроется диалог «Удалить контакт?», фокус на «Отмена». «Отмена», крестик и Esc закрывают диалог, контакт остаётся. Нажми «Удалить» в диалоге — откроется список: «Всего» на 1 меньше, контакт не находится поиском, внизу сообщение «Контакт удалён». Через 3 секунды оно исчезает, крестик закрывает сразу, после обновления страницы его нет. Старый адрес карточки отвечает «не найдено».

## База данных (PostgreSQL в Docker)

Локально в Docker работают Postgres и почтовая заглушка Mailpit («Вход и почта локально»). Порты открыты только на `127.0.0.1`, из сети они недоступны.

### Проверка

```bash
docker compose ps
```
В колонке `STATUS` у `postgres` и `mailpit` должно быть `healthy`.

Подключиться к базе через консоль:
```bash
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

### Изменение схемы

Поменяй `src/db/schema.ts`, затем:
```bash
pnpm db:generate   # создаст новую миграцию в drizzle/
pnpm db:migrate    # применит её
```

`pnpm db:migrate` запускает тот же `src/db/migrate.ts`, что и сервер при выкатке, и читает `.env`.

### Миграция входа на базе с данными

Миграция `0003_login` передаёт все существующие контакты и группы одному пользователю — владельцу приложения. Его почту она берёт из переменной `OWNER_EMAIL`: добавь в `.env` строку `OWNER_EMAIL=<твоя почта>` (регистр и пробелы по краям не важны). Если в `contacts` или `groups` есть строки, а `OWNER_EMAIL` пуста или не задана, миграция падает с сообщением про `OWNER_EMAIL`, и ничего не меняется: миграции идут одной транзакцией. На пустой базе (новая установка, CI) почта не нужна.

### Остановка

```bash
docker compose stop      # остановить, данные сохранятся
docker compose down      # удалить контейнер, данные сохранятся в volume
docker compose down -v   # удалить контейнер И ВСЕ ДАННЫЕ базы — необратимо
```

## Выкатка на сервер

Приложение работает на https://app.mypeoplecrm.ru. Выкатка автоматическая: **push в `main` — и через несколько минут новая версия на сервере.**

Что происходит после push (`.github/workflows/deploy.yml`):

1. **checks** — те же проверки, что на PR (`ci.yml`): lint, формат, типы, Vitest и e2e на пустой временной базе, сборка образа без публикации. Упали — дальше не идёт.
2. **build** — собирает Docker-образ приложения (`Dockerfile`) и кладёт в GitHub Container Registry с тегом — SHA коммита.
3. **deploy** — копирует всю папку `deploy/` на сервер в `/opt/personal-crm` и запускает `deploy/deploy.sh`: скачать образ → поднять базу → снять бэкап базы (не снялся — выкатка останавливается, миграции не применяются) → применить миграции разовым контейнером (упали — новая версия не стартует) → запустить новую версию → проверить `/health` → оставить на сервере только текущий и предыдущий образы.
4. Проверка снаружи: `https://app.mypeoplecrm.ru/health` отвечает 200.

Следить за выкаткой: вкладка **Actions** репозитория на GitHub. Зелёная галочка — выкатилось, красный крестик — нет (сервер продолжает работать на прошлой версии, если упало до шага «App»).

`pnpm start` локально пишет предупреждение `"next start" does not work with "output: standalone"` — это ожидаемо: сервер работает, а `standalone` нужен для Docker-образа.

### На сервере

- Пользователь `crm-deploy`, папка `/opt/personal-crm`: `compose.yml`, скрипты, `.env` (секреты, права 600, пишет только владелец), `image.env` / `image.env.prev` (текущая и предыдущая версия), `backups/` (бэкапы базы, права 700)
- В `.env` на сервере, кроме базы, — настройки входа и писем (список — `.env.example`): `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=https://app.mypeoplecrm.ru`, SMTP Resend (`smtp.resend.com`, порт **2465** — 465 хостинг закрывает, `SMTP_SECURE=true`, пользователь `resend`, пароль — ключ Resend), `MAIL_FROM` с адресом на домене `mail.crm.mypeoplecrm.ru` (подтверждён в Resend), `OWNER_EMAIL`. Без любой из настроек входа выкатка останавливается на первом шаге, до бэкапа и миграций. `E2E_AUTH_IP_LIMIT` на сервер не ставить
- docker compose, проект `prod`: `postgres` (данные в томе `prod_pgdata`) и `app` на `127.0.0.1:3000`; nginx проксирует на него `app.mypeoplecrm.ru`
- Порты наружу не открыты: база доступна только с самого сервера на `127.0.0.1:5433` (или через SSH-туннель)

Посмотреть состояние и логи (папка закрыта для других пользователей, поэтому сначала переключиться на `crm-deploy`):
```bash
ssh vps_hostkey
sudo -u crm-deploy -i
cd /opt/personal-crm
docker compose -p prod -f compose.yml --env-file .env --env-file image.env ps
docker compose -p prod -f compose.yml --env-file .env --env-file image.env logs --tail 100 app
exit
```

### Откат (только вручную)

Автоотката нет. Если новая версия сломана — вернуть предыдущую:
```bash
ssh vps_hostkey
sudo -u crm-deploy /opt/personal-crm/rollback.sh
```
Скрипт меняет местами текущую и предыдущую версии и перезапускает приложение; повторный запуск возвращает обратно. Миграции базы откат не отменяет — для этого восстановление из бэкапа (ниже).

Выкатку входа (миграция `0003_login`) один `rollback.sh` не откатывает — порядок в «Откат выкатки входа» ниже.

### Бэкапы и восстановление

**Бэкап** снимается автоматически при каждой выкатке, до миграций. Файл — `/opt/personal-crm/backups/<время UTC>-<SHA версии>.dump`, где SHA — версия, которая работала **до** выкатки, то есть данные под эту версию. Если на сервере ещё не было ни одной версии, вместо SHA стоит `initial`. Хранится только последний бэкап: после удачного нового старый удаляется. Формат — `pg_dump -Fc` (сжатый архив PostgreSQL).

Посмотреть бэкапы:
```bash
ssh vps_hostkey
sudo -u crm-deploy ls -l /opt/personal-crm/backups/
```

**Восстановление** — только вручную, запускает владелец:
```bash
ssh vps_hostkey
sudo -u crm-deploy /opt/personal-crm/restore.sh /opt/personal-crm/backups/<файл>.dump
```
Что делает скрипт:
1. Проверяет, что файл есть и это настоящий бэкап.
2. Показывает файл (размер, время), базу, которую он заменит, и версию приложения; ждёт ввода `yes`. Любой другой ответ — выход, ничего не меняется.
3. Снимает копию текущей базы — `backups/<время>-<SHA текущей версии>-pre-restore.dump`. Хранится только последняя такая копия, отдельно от бэкапа выкатки. Копия не снялась — дальше не идёт.
4. Останавливает приложение, удаляет базу, создаёт её заново и загружает бэкап.
5. Поднимает приложение **той же версии** и проверяет `/health`.

Если скрипт упал после остановки приложения, он печатает путь к копии данных до восстановления: из неё можно восстановить тем же скриптом.

**Версии.** Restore версию приложения не меняет. Бэкап содержит и таблицу применённых миграций, поэтому база после восстановления — ровно та, что была под версией из имени файла. Если приложение сейчас новее (например, после выкатки с миграцией), сначала верни версию из имени бэкапа (`rollback.sh`, если это предыдущая) — или следующая выкатка применит недостающие миграции заново.

Проверить после восстановления: `https://app.mypeoplecrm.ru/health` отвечает 200, в приложении — данные на момент бэкапа.

### Откат выкатки входа

Выкатка входа применила миграцию `0003_login`: у контактов и групп появился владелец (`user_id NOT NULL`). Поэтому откатывать её можно только вместе — прошлую версию приложения и базу из бэкапа, снятого перед этой выкаткой. Запускает владелец, на сервере:

1. `ssh vps_hostkey`, затем `sudo -u crm-deploy ls -l /opt/personal-crm/backups/`. Нужен бэкап этой выкатки: `<время>-<SHA прошлой версии>.dump`, его снял `deploy.sh` до миграции `0003`. Файлы `*-pre-restore.dump` не подходят
2. `sudo -u crm-deploy /opt/personal-crm/rollback.sh` — вернуть прошлую версию приложения. Сначала версия, потом база («Версии» выше). До шага 3 прошлая версия не может сохранять контакты и группы: схема уже новая
3. `sudo -u crm-deploy /opt/personal-crm/restore.sh /opt/personal-crm/backups/<файл из шага 1>.dump`, подтвердить `yes`
4. Проверка: `https://app.mypeoplecrm.ru/health` отвечает 200; приложение открывается без входа и показывает данные на момент бэкапа

Что важно знать:
- Всё, что любой пользователь (владелец и друзья) создал или изменил после выкатки, пропадёт: база возвращается к состоянию до выкатки. Копию базы перед восстановлением `restore.sh` снимает сам (`*-pre-restore.dump`)
- Отдельно один `rollback.sh` не работает: старая версия не умеет писать в схему с `user_id NOT NULL`. Отдельно один `restore.sh` тоже нет: новая версия не запустится на старой схеме
- Пока вход остаётся в main, следующая выкатка из main снова применит миграцию `0003` к восстановленной базе. Чтобы этого не было, вход нужно откатить и в main (revert PR)
